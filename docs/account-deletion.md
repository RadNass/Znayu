# Znayu: безопасное удаление взрослого аккаунта (проект функции, НЕ включено)

В репозитории подготовлен серверный код `supabase/functions/delete-account/index.ts`. **Публикация GitHub Pages не устанавливает его в Supabase.** На сайте нет работающей кнопки облачного удаления, пока функцию не установят и не проверят. Код не запускается автоматически и не меняет текущих данных.

## Что делает серверная функция

- Принимает только JSON POST с `confirmation: "УДАЛИТЬ МОЙ АККАУНТ"`.
- Проверяет заголовок `Origin` (только `https://radnass.github.io`) и действительную авторизацию пользователя через `withSupabase({auth:'user'})`.
- Определяет `user_id` только из **проверенного сервером JWT**, игнорирует любые указанные клиентом идентификаторы.
- Из Auth Admin API получает время последнего входа: он должен быть не старше 10 минут.
- Серверным клиентом удаляет только записи `znayu_analytics_events` с `auth_user_id` и `learner_progress` с `user_id` владельца, затем удаляет собственный Auth-аккаунт.
- Не передаёт секретный ключ в браузер; проверяет Content-Type и размер тела, не выводит персональные данные в ошибках.
- Удаление облачного аккаунта необратимо; браузер должен **после успешного ответа** выйти из аккаунта и очистить локальный взрослый профиль.

**Ограничения:** записи аналитики с `auth_user_id IS NULL`, данные провайдеров, резервные копии и технические журналы не удаляются этой функцией. Для них необходим отдельный регламент оператора и срок хранения. Функция требует существования обеих таблиц. Техническая проверка кода не равна независимому аудиту безопасности.

## Перед развёртыванием

1. Юридически подтвердить оператора и актуальный регион Supabase. До этого не расширять обработку пользовательских данных.
2. Проверить в рабочей базе RLS и права `learner_progress`, `znayu_analytics_events`, `znayu_analytics_admins`, а также наличие расписания удаления аналитики.
3. Убедиться, что тесты с двумя отдельными аккаунтами подтверждают удаление **только своих данных**; протестировать отклонение неподписанного запроса, чужого `user_id`, старого входа, неверного `Origin` и повторного запроса.
4. Проверить аудит, лимитирование запросов, поведение Supabase при частичном сбое, влияние на резервные копии и запросы на удаление анонимных событий.
5. Убедиться, что оператор может отвечать на запросы пользователей о доступе, исправлении и удалении данных и публикует реальный приватный контакт. **Не заменять им публичные GitHub Issues.**

## Развёртывание после проверок

Выполняется владельцем Supabase проекта с Supabase CLI, а не пользователем браузера.

```bash
supabase login
supabase link --project-ref hanyhyujcitwjlispwlq
supabase functions deploy delete-account
```

Рекомендуется оставить `verify_jwt=true` (настройка по умолчанию), использовать `withSupabase({auth:'user'})` и повторно проверять свежесть входа на сервере.

Серверные секреты Supabase доступны функции через окружение проекта, их **не нужно** добавлять в GitHub или JavaScript приложения. Убедитесь, что старый JWT не может использоваться после удаления и что повторный вызов возвращает ошибку авторизации.

## Почему онлайн-кнопка пока не включена

Невозможно удостовериться в безопасности удаления без испытания живого Supabase Auth и базы. Нужны проверка прав и явное одобрение владельца инфраструктуры перед активацией. До этого в Znayu есть экспорт данных и локальная очистка школьного профиля; удаление облачного аккаунта помечено как недоступное.

При переносе на свой домен скорректировать `ALLOWED_ORIGIN` и браузерные адреса в Supabase/Cloudflare.
